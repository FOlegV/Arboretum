Ниже — детальная архитектура и пошаговый план внедрения системы, которая соединяет PARA (организация по действенности), CODE (поток Capture → Organize → Distill → Express), метод Фейнмана (проверка понимания через объяснение) и интервальные повторения (закрепление в долговременной памяти) в одном хранилище Obsidian.

Сначала — «брейншторм» архитектуры: какие есть варианты и почему выбран гибридный, затем — конкретная структура и план.

Часть 1. Брейншторм архитектуры: три варианта и выбор
Вариант A: «PARA — единственная ось». Все заметки лежат в Projects / Areas / Resources / Archive, а Фейнман и повторения — просто теги или inline-карточки внутри этих папок.
Плюс: минимальная когнитивная нагрузка при захвате.
Минус: повторение и «объяснение» не имеют собственного рабочего пространства; трудно построить очередь «что учить сегодня» без сложных Dataview-запросов.

Вариант B: «Учебный трек поверх PARA». PARA остаётся для хранения (источники, проекты, области), но создаётся отдельная папка Learn/ с концепт-заметками, сессиями Фейнмана и очередью повторений.
Плюс: чёткое разделение «библиотеки» и «тренажёра»; легко автоматизировать очередь повторений.
Минус: риск дублирования: одна и та же идея может жить и в Resources/, и в Learn/Concepts/.

Вариант C: «Гибрид с MOC-слоем» (рекомендуется). PARA — физическая структура папок. Внутри Resources/ и Areas/ живут концепт-заметки (атомарные, с YAML-полями для повторения). Learn/ — это не «свалка», а тонкий слой сессий: сюда попадают только результаты работы по Фейнману (объяснения, пробелы, аналогии), которые ссылаются на концепт-заметки. Очередь повторений строится по YAML-полям концепт-заметок, а не по папке. MOC (Map of Content) связывают концепты по темам, не ломая PARA.

Почему C: CODE требует, чтобы Organize и Distill были разделены. Если пытаться делать всё в одной папке, «дистилляция» (прогрессивная суммаризация) и «объяснение по Фейнману» смешиваются с хранением источников, и система быстро деградирует в архив без повторного использования. Гибрид сохраняет PARA как ось действенности и даёт учебному циклу собственный управляемый контур.

2.2. YAML-схема концепт-заметки (ядро системы)
Единая схема — обязательное условие, иначе Dataview и повторения не соберутся в очередь.

yaml
---
type: concept
status: seed | growing | evergreen
created: 2026-11-02
source: "[[Название источника]]"
para_context: project | area | resource | archive
project: "[[Название проекта]]"        # если применимо
moc: ["[[MOC — Тема]]"]

# Поля для Фейнмана
feynman_status: not_started | explained | gaps_found | simplified
feynman_score: 0-3                   # по трём критериям (см. ниже)
last_feynman: 2026-11-02

# Поля для интервального повторения
review: true                         # участвует ли в очереди
review_due: 2026-11-03
review_interval: 1                   # дней
review_ease: 2.5                     # для SM-2 / FSRS
review_count: 0

tags: [concept, тема/подтема]
---
2.3. Шаблоны (Templater) — три обязательных
A. Шаблон концепт-заметки — тело состоит из трёх блоков: Определение своими словами → Механизм / «почему работает» → Границы применимости. Это сразу готовит заметку к Фейнману, а не к пересказу источника.

B. Шаблон сессии Фейнмана — четыре шага, встроенные в структуру заметки:

Выберите концепт → ссылка на [[Concept]].

Объясните просто (без терминов источника).

Найдите пробелы → список «что не смог объяснить».

Упростите и аналогизируйте → одна аналогия + одно ограничение.

C. Шаблон источника — метаданные (автор, ссылка, дата, тип), плюс поле distill_layer: 1|2|3|4 для прогрессивной суммаризации по Форте: источник → выделения → жирный шрифт → личное резюме.

Часть 3. Рабочие процессы: как система живёт
3.1. Поток CODE в терминах Obsidian
Capture. Всё, что потенциально полезно, попадает в 00_Inbox через QuickAdd. Правило Форте: захватывайте только то, что отвечает на один из ваших «12 любимых вопросов» (или явно служит активному проекту) — иначе inbox превращается в кладбище.

Organize. Ежедневная 5-минутная разборка: из 00_Inbox → либо в 01_Projects / 02_Areas / 03_Resources/Sources, либо в 04_Archive, если вещь больше не действенна. Критерий — не тема, а «пригодится ли это в ближайшем проекте».

Distill. Для источников — прогрессивная суммаризация: 1-й проход — выделить; 2-й — оставить только жирное; 3-й — написать личное резюме в 3–5 предложениях. Для концептов — сразу писать своими словами (это одновременно подготовка к Фейнману).

Express. Каждая сессия Фейнмана заканчивается артефактом: короткое объяснение, аналогия, список пробелов. Это и есть «выражение» знания — оно сохраняется в 05_Learn/Feynman_Sessions/ и линкуется к концепту.

3.2. Цикл Фейнмана ↔ повторения (связка, которую обычно теряют)
Распространённая ошибка — запускать интервальные повторения до того, как концепт понят. Повторение закрепляет понимание, а не создаёт его. Поэтому цикл такой:

Concept note создан → feynman_status: not_started.

Сессия Фейнмана → если объяснение провалено, feynman_status: gaps_found, концепт не попадает в очередь повторений; вместо этого создаётся задача «закрыть пробел».

Повторная сессия после закрытия пробела → feynman_status: explained или simplified; только теперь review: true и review_due устанавливается на завтра.

Spaced Repetition начинает вести интервалы. При каждом повторении можно открывать сессию Фейнмана заново (режим «объясни ещё раз, короче») — это одновременно и проверка, и повторение.

Плагин Feynman Learning реализует эту связку автоматически: он ведёт концепты по четырём шагам, оценивает объяснение по трём измерениям (простота языка, механизм, пример) и только после прохождения ставит концепт в очередь повторения с интервалами 1/7/30 дней. Его можно использовать как «второй пилот», если не хочется вручную писать Dataview-запросы, но базовая схема на YAML + Spaced Repetition остаётся переносимой.

3.3. Дашборды (Dataview) — три обязательных запроса
1. «К повторению сегодня»:

dataview
TABLE review_due, review_interval, feynman_status
FROM "03_Resources/Concepts"
WHERE review = true AND review_due <= date(today)
SORT review_due ASC
2. «Готовы к Фейнману» (концепты, которые ещё не объяснялись, но уже имеют достаточно содержания):

dataview
LIST
FROM "03_Resources/Concepts"
WHERE feynman_status = "not_started" AND status != "seed"
3. «Пробелы, которые блокируют повторение»:

dataview
TABLE file.link AS Concept, feynman_score
FROM "03_Resources/Concepts"
WHERE feynman_status = "gaps_found"

Часть 5. Что делает систему «рабочей», а не «красивой»
Один концепт — одна заметка. Атомарность нужна не для «чистоты», а чтобы интервальное повторение имело осмысленную единицу. Если заметка содержит пять идей, вы не знаете, что именно забыли.

Фейнман — ворота к повторению. Не ставьте review: true на концепт, который вы не смогли объяснить. Иначе вы будете «повторять» фразы из источника, а не понимание.

PARA по действенности, не по теме. Концепт из Resources/ может обслуживать Projects/ через линк; не переносите папки, просто обновляйте para_context и связи.

Дашборд важнее папки. Вы будете заходить в систему через «что сегодня повторить / что объяснить», а не через дерево папок. Если дашборды не работают — система мертва, даже если папки красивые.

Начните с 5 концептов, а не с 50. Система проверяется на малом объёме; если через неделю вы не открыли ни одной сессии Фейнмана, проблема в трении захвата или в слишком сложных шаблонах.

## 5. Уровни и гейты — то, что не даёт древу стать декоративным

Без гейтов «древо навыков» превращается в геймификацию ради галочек. Гейты должны требовать **артефакт**, а не клик.

| Уровень | Название | Гейт (что должно существовать в vault) |
|---|---|---|
| 0 | Locked / Aware | Заметка навыка создана, есть предпосылки |
| 1 | Theory | ≥1 концепт-заметка с `skill: [[этот навык]]` |
| 2 | Understanding | ≥1 сессия Фейнмана с `feynman_status: simplified` |
| 3 | Practiced | ≥1 закрытая задача/подпроект со ссылкой на навык |
| 4 | Proficient | ≥3 Feynman passed **и** ≥2 проекта, `review_count_avg` ≥5 |
| 5 | Mastered | Артефакт «объяснение для других» (MOC, статья, выступление) |

**Практика обновления счётчиков.** Два варианта:
- *MVP:* вручную в YAML после каждой сессии Фейнмана / закрытия проекта. 10 секунд работы, зато прозрачно.
- *Чисто:* **DataviewJS** в теле заметки навыка, который считает `feynman_passed` и `projects_applied` автоматически. Даю готовый сниппет, если нужно — но не вводите его на первой неделе, сначала проверьте систему руками.

**Правило обновления уровня:** уровень повышается **только при выполнении гейта**, а не «когда захотелось». Если гейт не выполнен — навык остаётся на текущем уровне, даже если кажется, что вы его освоили.

| 1 | Теория | ≥1 концепт со ссылкой `навык: [[этот навык]]` |

6. Технические оговорки (обязательно прочитать)
Русская схема работает в Obsidian, но есть три места, где нужна настройка:

Dataview. Ключевые слова (TABLE, FROM, WHERE, FLATTEN) — только английские. Русскими могут быть имена полей (повтор_до), папок (03_Ресурсы/Концепты) и значения ("упрощён"). Если попытаться написать ТАБЛИЦА — запрос не сработает.

Spaced Repetition. По умолчанию плагин ищет тег #review. Зайдите в настройки плагина → поле «Review tag» → замените на #повторение. Иначе русские заметки не попадут в очередь. Альтернатива — не использовать тег плагина, а вести очередь через YAML-поля + Dataview (как в §5).

Templater. Выражения (<% tp.date.now(...) %>) и методы (tp.file.title) — английские, это код. Русскими могут быть только имена файлов шаблонов и содержимое заметок.

Дополнительно:

Имена файлов на кириллице в Obsidian работают, но при синхронизации (Git, iCloud, Syncthing) возможны проблемы с нормализацией Unicode на macOS (NFD) vs Linux/Windows (NFC). Если планируете синхронизацию — либо проверьте настройки, либо оставьте имена файлов латиницей, а папки и поля — кириллицей.

Canvas с русскими именами узлов работает штатно.

Ссылки [[Python — основы]] и [[Навык — Python]] — кириллица в wikilinks полностью поддерживается.

Вот набор, разделённый на три уровня по критичности.

🔧 Обязательные плагины: без них система не соберётся
Это минимальный набор из ваших предыдущих планов. Без Templater схема YAML-полей расползётся, без Dataview очереди повторений и древо навыков останутся статичными списками.

Templater
Роль в системе: единая генерация заметок. Он отвечает за то, чтобы у каждого концепта, навыка, сессии Фейнмана и источника были одинаковые поля (тип, фейнман_статус, повторять, навык) и даты создавались автоматически. Без него вы очень быстро начнёте забывать поля, и Dataview перестанет находить заметки в очередях.

QuickAdd
Роль: снижение трения на шаге Capture (CODE) . Одна горячая клавиша — и мысль или выделенный фрагмент падает в 00_Входящие или сразу в 03_Ресурсы/Концепты. Без этого шаг «захвата» начинает саботироваться, и система теряет входной поток.

Dataview
Роль: вся динамика системы. Именно он превращает YAML-поля в рабочие списки: «что повторить сегодня», «какие навыки готовы к повышению», «у каких навыков нет теории». Без Dataview ваши папки останутся просто папками, а древо навыков — картинкой.

Spaced Repetition (st3v3nmw)
Роль: движок интервальных повторений. Он читает тег #повторение (его нужно заменить в настройках с #review на русский вариант) или inline-карточки и ведёт интервалы по алгоритмам FSRS / SM-2. У плагина есть полная русская локализация, так что интерфейс не будет мешать.

⚙️ Рекомендуемые плагины: сильно повышают практичность
Эти плагины не критичны на первой неделе, но без них система быстро упирается в потолок удобства.

Tasks
Роль: управление практическими задачами в Проектах и Областях. В вашей модели проектная задача со ссылкой на навык ([навык:: python-основы]) — это гейт для перехода навыка на уровень «Практика». Tasks умеет собирать чек-боксы со всего хранилища в единый список, поддерживает сроки и повторяющиеся задачи — это делает дашборд «Практика на сегодня» реальным, а не декоративным.

Excalidraw
Роль: визуальные сессии Фейнмана. На шаге «упрощение и аналогия» часто проще нарисовать схему, чем писать текст. Excalidraw позволяет встроить рисунок прямо в заметку-сессию, не разрывая контекст.

Advanced Canvas (или Canvas Mind Map)
Роль: удобная работа с Древо_навыков.canvas. Базовый Canvas в Obsidian умеет немного; эти плагины добавляют автоматическую раскладку дерева, управление ветками и иерархию. Это особенно полезно, когда узлов становится больше 15–20 и ручная расстановка начинает отнимать время.

Linter
Роль: гигиена YAML и Markdown. Он может автоматически форматировать frontmatter (порядок полей, кавычки, даты) и списки при сохранении. Это важно, потому что Dataview чувствителен к формату YAML: одна лишняя кавычка вокруг даты — и запрос «повтор_до <= date(today)» перестаёт находить заметку.

🧪 Опциональные: под конкретную задачу, не «на всякий случай»
Feynman Learning
Этот плагин делает ровно то, что вы описали в методологии: проводит через четыре шага, анализирует пробелы и только после прохождения ставит концепт в очередь повторения (по умолчанию интервалы 1/7/30 дней). Он может быть полезен как «второй пилот», если не хочется вручную связывать сессии Фейнмана и YAML-поля. Но есть нюанс: плагин активно использует AI (нужен API-ключ), а на первой-второй неделе, пока вы проверяете саму механику системы, он может добавить лишнюю сложность. Лучше ставить его после недели 3, когда базовый цикл уже работает вручную.

BRAT
Не самостоятельный плагин для работы, а установщик бета-плагинов. Он нужен только если вы захотите поставить Feynman Learning или другие плагины, которых ещё нет в официальном каталоге Obsidian. Если ограничиваетесь официальным каталогом — BRAT не нужен.

QuickAdd (у вас уже есть) остаётся центральным «шлюзом». Он создаёт заметки по шаблонам и заполняет YAML. Все остальные плагины этой категории либо вызывают QuickAdd, либо дополняют его.

Buttons позволяет встроить кнопку прямо в заметку (например, в дашборд 06_Система/Дашборды/), которая запускает шаблон Templater или макрос QuickAdd. В вашей системе это идеальный способ сделать «кнопку захвата» на видном месте: открыл дашборд → нажал «Новый концепт» → QuickAdd создал заметку с заполненным тип: концепт, фейнман_статус: не_начат, повторять: нет. Без кнопки вы каждый раз вспоминаете, какой шаблон и куда применять.

🗺️ Организация и навигация: доступ к нужному в один клик
Calendar (Liam Cain) — это навигатор по ежедневным заметкам, а не по проектам. В вашей системе он закрывает ритуал: «открыть день → проверить очередь повторений → отметить практику». Важно: Calendar создаёт ежедневные заметки и читает настройки Daily Notes. Если вы хотите, чтобы при создании дневной заметки Templater автоматически подставлял дашборд «Практика на сегодня», настройте создание дневных заметок через Calendar, а не через встроенный Daily Notes, иначе Templater не сработает.

Recent Files (Tony Grosinger) — хронологический список недавно открытых файлов в боковой панели. В системе с PARA и глубокой вложенностью это спасает от «я только что был в этом концепте, но потерял его». Роль утилитарная: не управляет логикой, просто ускоряет возврат к активному контексту. Ставьте его в панель рядом с дашбордами и не пытайтесь использовать как «источник правды» о том, что важно.

Tag Wrangler (PJ Eby) критичен для гигиены тегов, а не папок. В вашей схеме теги (теги: [концепт, тема/подтема]) могут накапливаться хаотично. Tag Wrangler позволяет переименовать тег во всём хранилище одним действием, сливать дубли и перетаскивать теги для реорганизации. Практическое правило: раз в 2–3 недели проходите по панели тегов и приводите тема/подтема к единому виду. Обязательно делайте бэкап перед массовым переименованием — операция потенциально необратима.

Commander — это «пульт» для команд и макросов: вы добавляете кнопки команд в ленту, на панель вкладок, в мобильный тулбар и создаёте макросы (последовательности команд). В вашей системе это способ собрать один клик для рутины: например, макрос «Начать сессию Фейнмана» = открыть шаблон сессии + создать заметку + перейти в неё. Commander не заменяет QuickAdd, а вызывает его команды. Хорошая связка: QuickAdd отвечает за логику создания, Commander — за то, чтобы эта логика была на расстоянии одного клика.

Callout Manager (eth-p) — визуальный слой для callout-блоков (> [!note], > [!warning] и т.д.). Он позволяет создавать кастомные callout’ы и менять их цвета/иконки. В вашей системе это не логика, а семантика чтения: например, в сессиях Фейнмана блок «Найденные пробелы» можно оформить как > [!gap], а «Аналогия» — как > [!analogy]. Это помогает быстро сканировать заметку глазами. Не встраивайте callout’ы в Dataview-запросы — они не влияют на данные, только на отображение.

⏱️ Выполнение и фокус: от «знаю» к «делаю» (PARA: Projects)
Здесь начинается зона практики, которая в вашей системе является гейтом для перехода навыка на уровень «Практика» (уровень 3).

Tasks (Clare Macrae) — это стандарт де-факто для задач в Markdown. Он собирает чек-боксы со всего хранилища по датам, приоритетам, тегам и статусам. В вашей системе Tasks — основной инструмент для дашборда «Практика на сегодня» и для гейта «≥1 применённая задача со ссылкой на навык». Задачи можно писать прямо в ежедневных заметках или в проектах, а Tasks соберёт их в один список. Важно: если вы используете русские имена полей в YAML, Tasks может их не увидеть, потому что он читает стандартные метаданные задач (даты в формате эмодзи-синтаксиса, теги, приоритеты). Ссылку на навык лучше держать в тексте задачи как inline-поле ([навык:: python-основы]), а не в YAML — тогда Dataview её увидит, а Tasks не сломается.

TaskNotes (Callum Alpass) — это другая философия: каждая задача — отдельная заметка, а представления (список, канбан, календарь, агенда) строятся поверх этих заметок через Obsidian Bases. Он умеет трекать время, вести историю сессий и даже синхронизироваться с Google Calendar. Для вашей системы TaskNotes — это тяжёлый, но мощный вариант, если вы хотите, чтобы каждая практическая задача имела свою заметку с полями навык, проект, статус и историей времени. Но есть конфликт: Tasks и TaskNotes решают одну проблему разными способами. Не ставьте оба сразу. Начните с Tasks (он легче и лучше ложится на существующие заметки). TaskNotes подключайте только если вам действительно нужны отдельные заметки-задачи и трекинг времени — например, для навыков уровня 4–5, где важна история практики.

Day Planner (James Lynch, continued by Ivan Lednev) превращает список задач в тайм-блоки на временной шкале дня. В вашей системе это способ связать «Практику» с реальным временем: вы блокируете 25 минут на задачу по навыку, и она отображается в дне. Нюанс: оригинальный плагин James Lynch имеет форки, и активная разработка идёт в форке ebullient/obsidian-day-planner-og. Если версия, которую вы указали, работает — хорошо; если начнутся баги, смотрите в сторону форка. Не пытайтесь использовать Day Planner как источник правды о задачах: источник — Tasks (или текст задачи), а Day Planner — только визуализация расписания.

Pomodoro Timer (eatgrass) — это таймер фокуса в статус-баре, который автоматически записывает сессии в дневную заметку и поддерживает inline-поля для трекинга задач. В вашей системе он идеально ложится на практику по навыку: запустили помидор → после сессии в заметке появилась запись → Dataview может собрать отчёт «сколько фокус-времени ушло на какой навык». Связка: Pomodoro Timer + inline-поле [навык:: …] в задаче → в конце недели вы видите, какие навыки реально получали время, а какие только числятся в древе.

Reminder (uphy) добавляет уведомления к TODO с датой и временем: напоминание всплывает в Obsidian и в системе. В вашей системе это «будильник» для дедлайнов проектов и для повторений, которые вы не хотите пропустить. Ограничение: на мобильных устройствах системные уведомления Obsidian не поддерживаются, поэтому Reminder работает в основном на десктопе. Если вы ведёте повторения через Spaced Repetition, Reminder может дублировать его очередь — не создавайте два параллельных механизма напоминаний об одном и том же.

Главный принцип интеграции
Плагины не должны менять вашу YAML-схему. Ядро системы — это поля тип, навык, фейнман_статус, повторять, повтор_до. Все перечисленные плагины либо читают эти поля (Dataview), либо помогают их заполнять (Templater, QuickAdd, Buttons), либо работают рядом с ними (Tasks, Pomodoro), не требуя переписывать структуру. Если какой-то плагин начинает диктовать вам, как называть поля или где хранить задачи (например, TaskNotes со своими Bases-файлами), — это сигнал, что он становится второй системой, а не «мышцей» первой. В таком случае либо принимайте его философию целиком, либо откажитесь.

Плагин Journals (автор srg-kostyrko) — это не просто замена встроенному «Календарю» или Daily Notes. Это мощный движок для создания иерархической системы периодических заметок, который может стать идеальным инструментом для ритуала «Ежедневный обзор» в вашей системе, но потребует замены некоторых ранее предложенных плагинов.

📔 Что такое плагин Journals и его ключевые возможности
Journals создан для управления заметками, привязанными ко времени. В отличие от стандартных плагинов, он позволяет создавать несколько независимых «журналов» для разных сфер жизни (например, «Личный», «Рабочий», «Учебный»).

Его ключевые возможности:

Гибкие интервалы: Поддерживает не только дни, недели, месяцы, но и произвольные периоды (например, спринты, семестры, кварталы).

Множественные журналы («Полки»): Можно вести отдельные журналы для работы и личных дел, не смешивая их.

Продвинутая навигация: Включает встроенный календарь, «хлебные крошки» для перехода между периодами (день → неделя → месяц) и настраиваемые блоки навигации прямо в заметках.

Шаблоны и автоматизация: Поддерживает шаблоны с переменными и полноценную интеграцию с Templater. Можно настроить автоматическое создание заметки на сегодня при открытии хранилища.

Метаданные и вопросы: Плагин может автоматически добавлять frontmatter в заметки и даже задавать вопросы при создании (например, «Какое настроение?» или «Какая цель на день?»), записывая ответы в поля.

🔄 Интеграция в вашу систему и совместимость
Главный принцип: Journals заменяет, а не дополняет плагины, отвечающие за ежедневные заметки. Разработчик прямо указывает, что он заменяет встроенные Daily Notes и Periodic Notes, а также плагин Calendar.

Вот как это влияет на вашу текущую конфигурацию:

1. Замена для Calendar и Daily Notes
Если вы установите Journals, то Calendar (Liam Cain) и встроенные Daily Notes вам больше не нужны. Journals предоставляет собственный календарь и систему создания заметок. Их настройки и данные не пересекаются. Вы просто используете один инструмент вместо трёх.

2. Идеальная связка с Templater
Ваша система уже построена на Templater, и Journals идеально с ним сочетается. При создании заметки журнала плагин сначала подставляет свои переменные (дату, номер периода), а затем автоматически запускает команды Templater внутри вашего шаблона. Это значит, что все ваши шаблоны для концептов, навыков и сессий Фейнмана будут работать и здесь.

## Определение своими словами
Списковое включение — это способ собрать новый список из старого одной строкой, сразу с условием и преобразованием. Вместо цикла с `.append()` вы пишете выражение, которое читается почти как фраза: «взять каждый элемент, отфильтровать, преобразовать».

## Механизм / почему работает
Python создаёт новый список в памяти, проходя по итерируемому объекту слева направо. Порядок частей важен: сначала `for`, потом `if`, потом выражение-результат. Внутри включения можно использовать условия и даже вложенные циклы, но читаемость падает быстро.

## Границы применимости
- Не работает как «замена всему»: если логика сложнее одного условия — обычный цикл читается лучше.
- Не подходит для побочных эффектов (печать, запись в файл): включение должно **возвращать** значение, а не делать что-то.
- Вложенные включения глубже двух уровней — почти всегда сигнал разбить на функции.

## Шаг 1. Концепт
Ссылка: [[Списковые включения]]
Что именно объясняю: «Зачем нужны списковые включения и когда их НЕ стоит использовать».

## Шаг 2. Объяснение простыми словами
Представьте, что у вас есть корзина яблок и вы хотите получить корзину чистых яблок без червяков и порезанных на кусочки. Вы не перекладываете каждое яблоко руками в новую корзину — вы описываете правило: «взять каждое яблоко, проверить, что оно целое, порезать и положить в новую корзину». Списковое включение — это и есть такое правило, записанное одной строкой. Программа сама проходит по корзине и собирает новую.

## Шаг 3. Найденные пробелы
- [x] Не мог сразу объяснить, что происходит с памятью: создаётся **новый** список, старый не меняется.
- [x] Путался, в каком порядке читать `if` и `for` внутри скобок.
- [ ] Не проверил на практике, что будет с вложенными включениями глубже двух уровней.

## Шаг 4. Упрощение и аналогия
Аналогия: включение — это **конвейер на заводе**, а не «короткий цикл». На конвейере каждая станция что-то делает с деталью, и на выходе — готовая деталь. Если конвейер слишком длинный и с развилками — его проще разбить на несколько цехов (функций), чем тянуть одну ленту.

Ограничение аналогии: конвейер работает с одной деталью за раз, а включение может содержать вложенные циклы — тогда аналогия «одной ленты» ломается.

## Обязательные поля концепта
`тип`, `статус`, `фейнман_статус`, `повторять`, `повтор_до`, `навык`.

## Правила
1. **Не более 10 полей на заметку.** Если хочется больше — вероятно, это две заметки.
2. **Даты — в формате `YYYY-MM-DD`**, без кавычек. Иначе `date(today)` в Dataview не сравнится.
3. **Имена полей — кириллицей, но без пробелов** (`повтор_до`, не `повтор до`).
4. **Статусы — из фиксированного списка**, не свободный текст. Иначе `WHERE фейнман_статус = "упрощён"` не найдёт заметку с опечаткой.
5. **Ссылки на другие заметки — в двойных кавычках** (`навык: ["[[Python — основы]]"]`), чтобы YAML не ломался.

## Файлы
- Концепт: `Название концепта.md` (например, `Списковые включения.md`).
- Сессия Фейнмана: `YYYY-MM-DD — Название концепта.md`.
- Источник: `Название (вид).md` (например, `Автоматизация рутины с Python (книга).md`).
- Навык: `Название навыка.md` (например, `Python — основы.md`).

## Папки
- Только кириллица, `_` вместо пробелов, цифровой префикс для порядка.
- **Не менять имена папок после создания** — Dataview-запросы привязаны к путям.

## Теги
- `тема/подтема` — предметная область (`тема/python/синтаксис`).
- `навык`, `концепт`, `источник` — тип заметки (дублирует YAML, но удобно для поиска).
- **Один тег — одно значение**, без синонимов.
